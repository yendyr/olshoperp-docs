Refactor status transaksional ke Enum — dampak, risiko & jalur aman

Feedback untuk Tech Lead: usulan merapikan pembacaan/penyimpanan status dokumen (draft, open, approved, void, …) dari string tersebar menuju enum, tanpa mengganggu pemakaian production yang sedang berjalan.

1. Verdict singkat

Arahnya benar untuk jangka panjang. Success-nya bukan di “ganti tipe kolom DB”, melainkan di PHP string-backed enum + kompatibilitas wire value + migrasi bertahap + 1 menu pilot.
PHP backed enum (string) + Eloquent cast bertahap; DB tetap VARCHAR
Paling aman
Tinyint / MySQL ENUM di awal project
Tinggi risiko
Big-bang semua menu + ubah skema DB sekaligus
Hindari

2. AS-IS di codebase (ringkas)

  • Status dokumen hidup sebagai string di kolom transaction_status.
  • Konstanta pusat di MainModel: TS_DRAFT = 'draft', TS_OPEN, TS_APPROVED, … (termasuk value seperti 'partially approved').
  • Pemakaian sangat lebar: ratusan file PHP + job + export + filter datalist + FE Vue.
  • Masih ada campuran MainModel::TS_APPROVED dan literal 'approved' → risiko typo & inkonsistensi.
Penting di Sales Order: ada dua sumbu status. transaction_status = lifecycle dokumen (draft/open/approved/void).
sales_order_process_status_id = pipeline fulfillment (sudah mirip “enum via FK/master”). Refactor enum harus jelas menyasar yang mana — jangan digabung diam-diam.

3. Rekomendasi arsitektur

Lakukan dulu

  1. PHP backed enum (string), mis. TransactionStatus.
  2. Value wire tetap sama: 'draft'|'open'|'approved'|… agar data & API lama kompatibel.
  3. Eloquent cast: 'transaction_status' => TransactionStatus::class.
  4. Query tetap memakai value string enum; kolom DB tetap VARCHAR.

Jangan mulai dari

  • ALTER kolom MySQL ke ENUM(...) global.
  • Rename value (approved → APPROVED) di fase awal.
  • Satu enum raksasa yang memaksa semua menu punya set status identik.
Kenapa urutan ini? Laravel sudah mendukung enum casting. API/FE bisa tetap terima string. Rollback mudah. Tidak ada lock ALTER besar di production. Constraint DB (check / tinyint) boleh jadi fase belakangan setelah PHP enum merata.

Bentuk enum yang realistis

  • Shared core untuk status umum: Draft / Open / Approved / Rejected / Void / Closed.
  • Per-domain / per-menu untuk outlier (Processed, Prepared, Partially Approved, Complete, Declined, …).
  • Atau: shared enum + allowlist legacy string sementara untuk value langka — dengan ticket follow-up.

4. Checklist dampak relasi (wajib ditinjau)

Area Yang perlu dicek
Inventaris nilai Distinct value per tabel (staging + sample production): typo historis, spasi, casing.
Shared vs menu-specific Jangan paksakan 1 enum untuk SO, PO, CBR, Journal jika set statusnya beda.
Dual status SO Pisahkan lifecycle vs process status; UI All SO sering gabungan keduanya.

Filter / search LIKE di datalist, advanced filter, export — banding objek enum vs string mudah bikin bug.
Approval log AS_APPROVED / timeline approval ≠ selalu sama dengan transaction_status.
Raw SQL / report / temp table Query dinamis & report yang hardcode VARCHAR status.
Jobs / queue Payload lama menyimpan string; worker baru harus tetap bisa baca.
Import / export Mapping label Excel (Draft) ↔ value (draft).
Policy / gate / can_update Cabang bisnis yang bergantung status.

5. Risiko utama

  1. Big-bang semua menu → regression masif (stock, journal, SO platform).
  2. Ubah tipe kolom DB dulu → lock table, deploy panjang, sulit rollback.
  3. Enum value ≠ string lama → query kosong / match gagal diam-diam.
  4. Strict compare setelah cast: $model->status === 'approved' jadi false jika masih membandingkan string vs objek enum.
  5. Satu enum global overfit → state invalid untuk menu yang punya status khusus.
  6. Partial deploy (BE cast on, FE/job lama) tanpa kompatibilitas string.

6. Step-by-step paling aman

  1. Fase 0 — Discovery Zero risk

    Inventory tabel + distinct transaction_status. Klasifikasi shared vs menu-only. Tulis matriks transisi per menu. Putuskan bentuk enum (shared + per-domain).

  2. Fase 1 — Introduce tanpa ubah perilaku Safe deploy

    Tambah TransactionStatus backed string. MainModel::TS_* tetap ada sebagai bridge (isi dari enum). Helper tryFromLoose / values() / labels(). Unit test round-trip. Belum wajib cast model.

  3. Fase 2 — Pilot 1 menu Controlled

    Pilih menu relatif tenang (bukan All SO dulu jika bisa). Cast satu model. Ganti compare ke enum; JSON tetap emit string. Regression create→open→approve→void + filter + export. Monitor log 1–2 minggu.

  4. Fase 3 — Perluas per modul Incremental

    Omni → SCM → Accounting. Satu PR = satu menu/modul. Jangan campur refactor status + fitur bisnis. CI grep: larang literal status baru di path yang sudah dimigrate.

  5. Fase 4 — FE alignment Parallel

    Value dari BE (shared const / OpenAPI / generated types). Label display terpisah dari value. Jangan ubah query param filter tanpa versioning.

  6. Fase 5 — Bersihkan legacy Optional

    Deprecate MainModel::TS_* setelah 0 pemakaian. Hapus literal string. Baru pertimbangkan DB check constraint / tinyint — dual-write jika perlu.

Sengaja ditunda MySQL ENUM column change global · rename value · menggabungkan process status SO ke transaction status.

7. Catatan khusus All Sales Order

  1. Enum lifecycle saja untuk transaction_status.
  2. Biarkan sales_order_process_status_id seperti sekarang.
  3. Document di technical: kapan UI memakai lifecycle vs process status.
  4. Bersihkan literal 'approved' di cabang yang sudah campur konstanta.
  5. Baru cast model SalesOrder + API resource setelah pola pilot terbukti.

8. Next action yang murah

  1. Acc arah: PHP string-backed enum dulu, bukan ubah kolom DB.
  2. RFC 1–2 halaman: shared vs per-menu + daftar value distinct dari DB.
  3. Pilih 1 menu pilot (disarankan bukan ASO di gelombang pertama).
  4. Setelah pilot hijau → backlog bertahap per modul.
Ringkas untuk keputusan Tech Lead Setuju refactor ke enum untuk ketahanan jangka panjang. Eksekusi = kompatibilitas value string + migrasi bertahap. Hindari big-bang skema DB. Pilot dulu, baru All Sales Order.
